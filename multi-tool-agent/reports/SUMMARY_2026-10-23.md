# 把知识库从「每次重启干等一分钟」改成「打开即用」——2026-10-23 工作总结与复盘

> **这份报告有两个读者**：不懂技术的人看 §1~§2 与 §9（术语小抄）；未来的自己看 §3~§8（数据、复盘、约束）。
> **口径**：所有数字都来自本机实测；凡是由实测单价外推的数字，一律标注「推算」。

---

## 1. 一句话结论

今天把项目的知识库从「能导入、能搜，但**每次程序重启后的第一次搜索要干等 52 秒**」改成了「**打开就能用（0.25 秒）**」，并用 2000 篇真实代码文档做了第一次负重压测，同时定下了一条新规矩：**以后所有工程改进，都要按 10 万 / 100 万 / 1000 万条数据来设计**，而不是按眼前几百条来设计。

如果只向老板汇报一句：**今天解决的不是「搜得准不准」，而是「要等多久」——而且顺手量出了「数据涨 1000 倍会先坏在哪里」。**

## 2. 给不懂技术的人：今天到底做了什么

先讲一个比喻，后面所有事都围绕它。

### 2.1 比喻：给每段文字在巨大的地图上定坐标

- 计算机看不懂「意思」，只懂数字。所以系统会把**每段文字翻译成一串数字**（1024 个小数），这串数字可以理解为**这句话在一张超大地图上的坐标**。意思相近的句子，坐标也靠得近。
- 这个「翻译」动作有个专业名字：**embedding（向量化）**。
- 关键点：**这件事必须真的算，不能凭空得到。** 就像把一本书翻成外语，翻一遍要花时间；你不把译文存下来，下次还得重翻。

### 2.2 之前的问题：翻译完就把译文扔了

- 系统把 979 篇文档切成了 1107 段，每段都算过坐标——**算一遍要 52 秒**。
- 但这些坐标只放在**内存**里（相当于草稿纸）。程序一重启，草稿纸被清空，**下次搜索要重新翻一遍**，于是用户看到的就是「转圈 52 秒」。
- 更糟的是：只要改动任意一篇文档，整张草稿纸都会被作废，又要重算全部。

### 2.3 今天做的四件事

| # | 做了什么 | 大白话 |
|---|---|---|
| 1 | **写了一个「文档导入器」** | 以前系统只知道文件叫什么、多大（像图书馆只登记书名不登记内容）；现在能把正文读进去、切成段、编好目 |
| 2 | **把翻译结果存进硬盘（持久化）** | 52 秒算出来的坐标写进数据库，重启后**直接读文件**，不再重算 |
| 3 | **只重算"变过"的文档** | 改一篇文档，就只重算那一篇，不再全库重来；换模型/换切法才全部重做 |
| 4 | **拿 2000 篇真实代码压测** | 量出「每段约 47 毫秒」「一篇文档约占 39KB」这些单价，用来推算数据涨 100 倍、1000 倍时会怎样 |

### 2.4 效果

| | 改之前 | 改之后 |
|---|---:|---:|
| 重启后第一次搜索 | **52.3 秒** | **0.25 秒**（约 212 倍） |
| 代价 | — | 硬盘多占 **2.7 MB** |
| 改一篇文档 | 整库重算 | 只重算这一篇 |

## 4. 复盘 A：我今天明确做错的地方（有证据）

| # | 错误 | 后果 | 根因 | 已经怎么处理 |
|---|---|---|---|---|
| 1 | 第一次导入时把 `reports/runs/` 里 **323 份按 run 生成的报告**也灌进了知识库 | 一口气写了 4,334 条噪声条目 | 动手前没先看目标目录的构成（哪里是真知识、哪里是自动生成物） | 加了 `--exclude` 与 `--replace`，清空重导，最终 395 条 |
| 2 | 压测用的 JSONL 是 6.4MB，被默认「单文件 2MiB 上限」**整份跳过** | 第一次压测只跑了 0.3 秒、导入 **0 条**，我一度以为脚本坏了 | 默认值对真实语料太紧；跳过提示只在汇总行里出现，不够显眼 | 显式传 `--max-file-bytes` 重跑并记录 |
| 3 | 关闭数据库连接的代码写在了「建索引」**之前** | 第一次构建报 `The database connection is not open` | 写代码时的先后顺序疏漏 | 已调换顺序 |
| 4 | 编辑代码时误删了一行 `const action = ...` | 编译会报错，属于低级失误 | 替换代码块时连带删掉相邻行 | 回读文件发现并补回 |
| 5 | 依赖本机 Ollama 服务，但**没检查它是否在运行** | 第一次建索引直接 `fetch failed` 失败 | 本机有三样外部依赖（Ollama / Docker / MCPHub），没有统一的前置健康检查 | 手动拉起服务后重跑成功；这件事记进「遗憾」 |

## 5. 复盘 B：判断上的失误（比手滑更值得记）

| # | 失误 | 为什么说它更严重 |
|---|---|---|
| 6 | **优先级排错了**：语料涨到 979 篇时，最先该修的是「用户要等 52 秒」，我却先去做了「提升检索准确率」的事（评测集、rerank） | 准确率当时在 60~72% 区间徘徊；把 52 秒变成 0.25 秒带来的体验提升，远大于多命中 2 个百分点。**可用性和质量不是一个量级的收益** |
| 7 | **先下结论、再扩样本验证**：18 条查询时得出「某参数最优」「向量召回 94%」，扩到 34、51、61 条后结论被自己推翻 | 这是方法论错误——应该先冻结评测集，再谈提升；前两轮的结论只能作废重写 |
| 8 | **评测语料一直没冻结** | 今天复跑评测时，语料已经从 19 篇 / 151 段涨到 23 篇 / 219 段，导致「今天 vs 昨天」的数字**不可直接比较**。没有稳定的尺子，所有「变好了」都无法证明 |
| 9 | **只测了「重启」这条路径，没测「改一篇文档后立刻搜索」** | 后者才是日常最常见的路径；现在它会在下次检索时同步补齐（预计几百毫秒），我**没有量这个数** |

## 6. 复盘 C：遗憾（知道该做但没做）

1. **没有后台补算**：新写入的内容仍会在下次检索时同步补齐，用户在那一瞬间仍要等几百毫秒。核心诉求「不占用户时间」只解决了一半。
2. **前端看不到「正在建索引」**：只有转圈，没有进度和原因，用户无法判断是卡住还是在干活。
3. **两套向量检索并存**：旧的 256 维哈希向量（977 条）与新的 1024 维模型向量是两条路，走不同接口会得到不同质量的结果，容易让人误判。
4. **没做真实 HTTP 端到端**：只用脚本模拟重启，没有「起服务 → 网页点搜索 → 计时」这一步。
5. **数据集结论只写在报告里**：LCC 只能当压测素材、不能当知识库——这个判断应该同时写进 README，避免下次再踩。
6. **`MAX_RAG_DOCS = 50,000` 这个硬上限没动**：到 10 万条会直接拒建，而它现在只出现在代码里，没有任何提示。

## 7. 复盘 D：为什么没有更早做（直接回答）

不是「不知道要持久化」，而是**三个判断叠在一起**：

1. 昨天知识库只有 225 篇 / 253 段，冷启动 **8.3 秒**——感知不到，所以被归为「可优化项」；
2. 今天导入后变成 979 篇 / 1,107 段，冷启动 **52 秒**——成本随文档数**线性放大**，但人的痛感是**跨过阈值才出现**；
3. 我在路线图里把「持久化」排成了 Step 1，却先做了 Step 2 的「提质量」——**把手段的先后顺序当成了优先级，而不是按用户痛感排序**。

一句话教训：**当数据量在增长时，先修「等待和失败」，再修「准不准」。**

## 8. 现在的边界，和下一轮的标准

### 8.1 还不能做什么

- **10 万篇**：会被 `MAX_RAG_DOCS=50,000` 直接拒绝；且现有重建方式是「全表读进内存」，这是最后能这么干的规模。
- **100 万篇**：索引要离开内存（改用数据库里的向量索引），重建从 15 小时（推算）级别改成必须 GPU + 严格增量。
- **1000 万篇**：单机单进程形态不成立，需要「服务 + 专用向量库 + GPU 入库 + 分片」。
- 以上三档的耗时都是按今天量到的单价**推算**，不是实测。

### 8.2 下一轮的验收标准（可量化）

| 指标 | 目标 |
|---|---|
| 检索耗时 p50 / p95 | < 200ms / < 500ms |
| 写入到可检索 | < 5 秒，且**不阻塞**正在进行的查询 |
| 冷启动 | < 1 秒（当前 0.25 秒） |
| 结果可解释 | 每条结果标明来自哪一段、走的哪条召回路径 |

### 8.3 下一轮顺序（按收益/成本）

1. **把「索引存在哪」抽象成可替换接口 + 改流式构建**（同时解决 10 万和 1000 万两个方向，且不改检索结果）
2. **后台补算**（写入不挡检索）
3. **冻结评测语料**（没有稳定的尺子，后面所有数字都白说）
4. **正文只存一份**（现在存了三份，规模上去是 300~500GB 的浪费）

## 9. 给非技术读者的小抄

| 术语 | 大白话 |
|---|---|
| **向量 / embedding** | 把一段文字翻译成一串数字，相当于给它在一张巨大的「语义地图」上定个坐标；意思越近，坐标越近 |
| **切块（chunk）** | 长文章没法整篇定一个坐标，所以切成小段，每段一个坐标 |
| **索引** | 地图的目录。没有目录，每次找东西都要走遍整张地图 |
| **冷启动** | 程序刚启动、脑子还是空的；这时第一次找东西最慢 |
| **持久化** | 把辛苦算出来的结果写到硬盘，下次直接读，不用重算 |
| **重建（rebuild）** | 把整张地图重新做一遍 |
| **增量** | 只改变化的那一块，不重做整张地图 |
| **指纹** | 给「用哪个模型、怎么切段」拍个身份证；身份证变了，就必须全部重做，避免新旧混着用 |
| **Rerank（重排）** | 先粗筛 20 条，再逐条细看重新排序（更准但更慢） |
| **Recall@5** | 正确答案有没有出现在前 5 名里 |
| **p50 / p95** | 一半的人 / 95% 的人在这个时间内完成 |

## 10. 一页纸总结

- **今天最重要的一件事**：把「每次重启后的 52 秒等待」变成「0.25 秒」，代价是 2.7MB 硬盘。
- **今天最大的教训**：先修体验（等待、失败），再修准确率；并且**先冻结尺子**再谈提升——否则涨没涨说不清。
- **今天最值得保留的做法**：先量后改、检索代码不动、把「推算」和「实测」分开写。
- **今天最该改但还没改的**：索引仍假设在内存里（10 万条就会撞墙）、写入仍会挡检索、评测语料仍在漂移。
- **明天第一件事**：把索引抽象成可替换接口 + 流式构建，同时为 10 万与 1000 万两个方向留出通路。
