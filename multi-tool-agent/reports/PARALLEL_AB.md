- **三组**（A 组是 A2 的"预算不足"对照点）：

## 3. 结论（诚实版）

**在当前实现与这类"广覆盖审计"任务上，编排并行没有省时间也没有省钱——它是"用约 7 倍 token 买分区覆盖与逐子任务证据"。**

1. **串行基线本身可用**：一个 codebase Agent 在 39.4s / 221k token / $0.0096 内完成了同一任务（产出结构化清点表 + 审计结论，质量并不差）。这直接回答了"要不要上多 Agent"——**这个任务形态下，不需要**。
2. **编排的成本结构被三条链路放大**（均可从数据指认）：
   - **重复读取（无上下文共享）**：15 个子任务各自独立读文件——`read_file` 调用 159 次 vs 串行 27 次，同一份代码被反复读、反复进 prompt；
   - **`search_files` 静默陷阱的连锁放大**：B 的 `unresolved` 里**自己报告**了"search_files 内容检索疑似失效（对确定存在字符串返回 0），改用逐行通读补偿"——逐行通读正是 1.39M 子任务 token 的主要来源（该陷阱见 `reports/CODE_REVIEW_2026-10-13.md` 之外的新发现，修复优先级应上调）；
   - **重试链的串行化**：15 个子任务中 3 个 maxToolCalls 中断、1 个输出截断失败、3 个取消，重派导致并行波（宽度 4）被重试吞掉——243.7s 的墙钟里可观的份额是重派，而不是并行度不足。
3. **编排真正买到的东西**（所以它不是"没用"，是"贵在别处"）：
   - **分区覆盖与逐子任务证据**：每个子任务有独立 objective / 证据 / 置信度，最终 15 个分区无遗漏；
   - **自报缺口**：`unresolved` 如实列出中断记录、疑似失效的工具、低置信项——单 Agent 的 221k 单一上下文里没有这种"结构化自检"；
   - **故障隔离**：单个子任务失败不拖垮整体（对比 A 组直接无产出）。
4. **什么场景才值得上编排**（据本次数据的推论）：
   - 单 Agent 上下文**装不下**（本任务 221k 装下了——先测这个上限，再决定）；
   - 子任务**低重试、高并行**（本例被重试链毁掉并行度）；
   - 需要**独立评审/交叉验证**（B 的自报 `unresolved` 是这种价值的雏形）。

## 4. 行动建议（按性价比）

1. **先修 `search_files` 三重陷阱**（`kind` 默认 / `|` 被转义 / `path` 被丢弃）——它同时污染"单 Agent 效果"和"编排成本"两条线；修完应重跑本 A/B，编排成本预计显著下降。
2. **给子任务加"已读文件"共享或缓存**：15 个子任务重复读同一批文件是结构性浪费；最小改动是为同一 run 内的子任务提供只读文件内容缓存（或让主 Agent 预读后作为 inputs 下发）。
3. **编排默认门槛**：主 Agent 派发前先判"这活儿一个上下文能否装下"（可用预筛 + 估算），装得下就走单 Agent。
4. **重试纪律**：连续 maxToolCalls 中断时应先"收窄分区"再重派（B 后期实际这么做了，但其代价已被计入）——把"收窄重派"提前为首次失败即触发。

## 5. 口径与边界（避免误读）

- **单次运行、单一任务、单一模型**：本文是"量化对照"不是"统计结论"；要做统计需 N 次重复取分布（建议 ≥5 次并用 trace span 对比墙钟）。
- **A2 与 B 不是"等预算"**：B 的结构是"顶层预算 + 每个子任务契约预算"（这正是编排的成本形态）；顶层预算三者相同（12 步 / 12 模型调用 / 200k token，A/A2 分别为 24/60 工具）。
- **成本为表价估算**（DeepSeek $0.14/1M 输入、$0.28/1M 输出、缓存 $0.0028/1M），真实账单以供应商为准。
- **缓存影响**：B 的输入大量命中缓存（子任务读同样文件），若不看缓存，原始输入 token 更高——成本数字因此"对编排友好"，仍不改变 7× 的结论。

## 6. 预筛闸门后的默认行为（2026-10-23，结构性更新；**未重跑 A/B**）

第 4 节的建议 ③（「装得下就别编排」）已落地为 `src/runtime/orchestrationGate.ts`，但本文的 7× 数字**没有变化**——
它们是闸门上线前测的，不能拿来说「成本已解决」。

现在自动分流的行为：

- 扫描目标仓库（跳过隐藏目录/符号链接；最多 4000 文件 / 32MB / 800 目录 / 深度 12）；
- 估算单上下文能否装下：`bytes / 3.2 + 8000 <= tokenBudget × 0.8`；
- 命中多信号（交叉验证 / 独立评审 / 分区审计 / 并行等）或扫描被截断 → 仍建议编排；
- **显式选择 orchestrator 不强制降级**，但 gate 会写进响应、`run_started` 与（开自检时的）主 Agent 提示；
- 自动分流原本给 orchestrator、但 gate=`single` 时降为 `codebase`，并在 `reason` 里写明「编排预筛：…」。
