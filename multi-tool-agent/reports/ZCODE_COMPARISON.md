# ZCode 对标分析与逐步优化建议

> 调研对象：**ZCode**（Z.ai 智谱开源的 coding agent，zai-org/ZCode，"Agentic Development Environment"）。
> 对比方法：ZCode 未在本地跑基准（桌面端 + GLM 专属计划），**对比基线取自其公开架构文档与源码结构分析**；**你项目一侧全部为真实遥测数据**（data/runtime.db，n=238 次真实模型调用 / 38 次真实运行）。
> 生成时间：2026-10-13。

---

## 一、ZCode 流畅性背后的关键技术机制（调研结论）

ZCode 的"流畅"不是单一模型快，而是**六个子系统协同**的结果：

### 1. 回合状态机（turn-machine）
一次对话回合是**显式状态机**而非松散 while 循环：`处理输入 → 等待模型 → 流式输出 → 调度工具 → 等待授权 → 执行工具 → 汇总 → 完成`，非法状态转移直接抛错。驱动循环每轮先清空 pending 命令与 steering 消息、跑**微压缩**、临近上下文上限时触发 auto-compact（带"防抖"防止压缩风暴）、按回合过滤工具表，**然后**才发起模型请求。
→ 流畅性来源：每个阶段有明确归属，出问题能立刻定位；压缩在请求前完成，不打断用户体感。

### 2. 依赖感知 + 安全感知的工具调度
工具注册表带丰富元数据（只读/破坏性/并发安全/授权要求/超时/输出预算）。模型返回一批调用时，调度器**建依赖图 → 拓扑排序 → 分并行波**；只读工具默认并行，破坏性永不并行，并发上限 10；权限解析织入同一管线（需授权的调用把回合停在 AwaitingPermission 阶段，不阻塞其它波）。
→ 流畅性来源：一批工具调用真正并行执行，权限等待不冻结其它工作。

### 3. 子代理 = 子运行时（不是 prompt 字符串）
子代理各自持有**独立 AgentRuntime**：过滤后的工具集、借用的 MCP、镜像的工具事件、消息 steering 下沉；支持前台/后台、长任务自动转后台、闲置监视、完成回通知父会话。内置只读 Explore 专家与通用 researcher 两个 profile。
→ 流畅性来源：脏活外包，主上下文不被污染；后台化让用户不必干等。

### 4. 上下文工程（压缩、外置、按需召回——而非截断）
- prompt 由 builder 从"静态段 + 动态源"组装；
- **microcompaction（步间）+ 手动 compact + 策略驱动 auto-compact（近限时）** 三层压缩；
- **跨会话项目记忆循环**：自动提取并召回持久知识；
- system-reminder 在对话中动态注入系统提示。
→ 流畅性来源：上下文体积稳定，长会话不"越聊越慢"。

### 5. 模型适配层吸收厂商噪声
流式执行包裹**重试预算、流空闲超时、流式工具调用装配器、严格工具 schema 校验**、OAuth；核心循环只看到干净的事件流，适配层处理"这到供应商之间会坏的一切"。
→ 流畅性来源：瞬时抖动被适配层吃掉，用户几乎感知不到。

### 6. 产品层配合
GLM-5.2/5.3 深度集成（IndexShare：1M 上下文下 per-token 计算降 2.9×；思考分级 Low/High/Max 按任务换速度）、执行模式（Ask/Edit-auto/Plan/Full-access）、**Goal Mode**（可验证目标 → 自主多轮 plan/execute/test/review → 完成校验 + 状态恢复）、`@`文件引用 / `#`历史会话链接 / `/`命令 / `$`技能、长文本自动转附件、AGENTS.md 项目约定、MCP(stdio/http/sse) + 插件 + 7 个生命周期钩子、会话 fork、远程控制。

**一句话总结**：ZCode 的流畅 = *流式装配（快）+ 并行波（密）+ 压缩外置（稳）+ 子代理隔离（净）+ 适配层容错（韧）*。

## 二、对比测试结果（四个维度）

| 维度 | 你的项目（实测） | ZCode 机制/达标线 | 差距判定 |
|---|---|---|---|
| **响应速度** | 模型调用 P50 **1.9s**、P95 **13.1s**、P99 20.2s（n=238）；运行总时长 P50 **10.5s**、P95 **71s**、max 160s（n=38） | 流式工具调用装配（首字节即反馈）、并行工具波、重试预算兜底瞬时抖动、思考分级（简单任务用 Low） | **中**。P50 尚可，长尾大：P95 13s 主要是 thinking 模式 + 工具串行等待 + 无流式工具装配 |
| **代码生成质量** | 定位是**只读分析 agent**（无写文件/编辑工具）；真实完成率约 **60%**（23/38），失败主因 MODEL_ERROR×8、limit_reached×7；工具失败累计 138 次 | Plan→Code→Review→Learn 闭环 + 编辑工具 + 红绿测试门 | **大（定位差异）**。无"生成-验证-修正"闭环；且无编辑能力（见建议 #8/#9 的适配路径） |
| **上下文连续性** | 最近 6 轮窗口 + 滚动摘要（提取式，今日新上）+ 知识库（FTS5 + sqlite-vec 语义召回）+ 全量 turns 持久 | microcompact（步间）+ auto-compact（token 感知、防抖）+ 跨会话项目记忆 + `@` 文件显式引用 + AGENTS.md | **中**。窗口+摘要已对齐方向，但**不感知 token 水位**（不知离上限多远）、摘要非真归纳、检索结果**不自动注入**新任务、用户无法 `@` 指定文件 |
| **错误处理** | ErrorReporter 四要素 + 错误码分类 + OUTPUT_TRUNCATED 可定位消息 + 单次调用 120s 超时 + 孤儿回收 + /api/errors 三落点 | 适配层重试预算 + 流空闲超时 + bounded retry + reviewer 红绿门 + **错误→学习闭环**（沉淀 correction notes） | **中**。报告/定位做得好（这点甚至更细），但**无重试**（MODEL_ERROR×8 一次失败即终）+ **错误不沉淀为规则** |

> 说明：MODEL_ERROR×8 是你真实运行最大的失败源——其中相当部分是 429/网络瞬断，在 ZCode 的适配层里会被重试预算吃掉，根本到不了"任务失败"。

## 三、逐步优化建议清单（按 ROI 排序）

### P0-1 模型调用重试预算（适配层）
- **问题**：8 次真实运行败于 MODEL_ERROR，一次瞬时 429/网络错就把整个 run 打成 failed；P95 13s 长尾里也含可重试的抖动。
- **与 ZCode 差异**：ZCode 的 model adapter 有 retry budget + stream idle timeout，核心循环只见干净事件流；我们的 OpenAIProvider 一次失败直接上抛。
- **优化方向**：`OpenAIProvider.chat` 加 ① 429/5xx/网络错的指数退避重试（预算 2 次，尊重 `Retry-After` 头）；② 流式 **idle 超时**（>30s 无增量则 abort 重试一次）；③ 重试耗尽才报 MODEL_ERROR，且错误消息注明"已重试 N 次"。
- **预期收益**：真实完成率 60% → 75%+；P95 长尾显著收窄。

### P0-2 Token 水位感知 + 自动压缩触发
- **问题**：tokenBudget×3、maxSteps×1 的 limit_reached 是"撞墙才知道"；每次调用离上限多远完全不可见。
- **与 ZCode 差异**：ZCode 三层压缩（microcompact 步间 / auto-compact 近限触发且带防抖），压缩发生在请求前；我们只有"固定截 6 轮"，与 token 无关。
- **优化方向**：Budget 已累计每次 promptTokens——当单次 prompt 超过阈值（如 60% 预算）时**自动触发滚动摘要压缩历史**（extractiveSummarize 已就绪，只差接线）+ 事件里报 `contextUseRatio` + UI 显示"上下文水位条"。
- **预期收益**：limit_reached 基本消除；长任务不再中途腰斩。

### P1-3 工具并行波（依赖感知调度）
- **问题**：工具并发虽有上限 4，但是"到一批就并发跑"，无依赖概念；模型的一批调用里只读操作白白串行。
- **与 ZCode 差异**：ZCode scheduler 建依赖图、拓扑排序、分**并行波**；只读默认并行、破坏性永不并行。
- **优化方向**：AgentRuntime 执行工具批次时，对**只读工具**（list_files/read_file/search_files/dir_stats）直接整批并行（我们全部工具本来就只读，这条尤其适用）；保留输出预算与错误隔离。
- **预期收益**：工具段耗时约降 40-60%，直接压运行 P95。

### P1-4 流式工具调用装配（首字节反馈）
- **问题**：现在等模型完整返回才解析 toolCalls；thinking 模型下用户盯 10s+ 空屏才知道要调什么工具。
- **与 ZCode 差异**：ZCode 有 streaming tool-call assembler，工具名一出就能显示"正在准备调用 X"。
- **优化方向**：`chatStreaming` 的 `accumulateOpenAIStreamChunk` 已增量聚合 tool_call 分片——加一个实时事件：检测到 tool_call 分片首帧即 `emitLive`"工具 X 准备中"，前端工具卡片提前渲染骨架。
- **预期收益**：体感流畅度提升最大的一项（用户从"等 10s"变"0.5s 见到动静"）。

### P1-5 `@` 文件级上下文入口
- **问题**：用户无法显式说"就看这个文件"；agent 靠 search 摸索，平均多耗 2-3 次调用（真实运行平均 6.4 次工具调用，其中不少是探索性搜索）。
- **与 ZCode 差异**：ZCode `@` 引用文件/文件夹，把高相关上下文直接喂给模型。
- **优化方向**：goal 输入框支持 `@相对路径` 语法：前端解析后把文件列表放进请求，system prompt 注入"用户指定：直接从这些文件开始，不要先探索"。零后端改动即可落地（拼进 goal 或 contextSummary）。
- **预期收益**：平均每任务省 2+ 次模型往返 ≈ 省 4-6s 和数千 token。

### P2-6 错误 → 学习闭环（correction notes）
- **问题**：138 次工具失败、8 次 MODEL_ERROR 只进报告，从不沉淀；同样的坑换个会话再踩一遍。
- **与 ZCode 差异**：ZCode 生态（及 Rust 系 zcode 变体）有 self-learning：高频错误模式归纳为持久 correction notes，后续任务自动注入。
- **优化方向**：知识库已就绪——写个汇总脚本：从 audit/errors 提取 top 错误模式（如"max_tokens 截断""参数用别名"）→ `putData` 到 collection `lessons` → 构建新任务的 system prompt 时检索注入 1-2 条最相关"已知坑"。
- **预期收益**：重复错误递减；这正是你"定期看报告"诉求的自动化延伸。

### P2-7 LLM 摘要器升级（真归纳）
- **问题**：滚动摘要目前是提取式（词法压缩），长对话中"结论性"信息保留率有限。
- **与 ZCode 差异**：ZCode compact 用模型做归纳，且有跨会话项目记忆循环。
- **优化方向**：`ContextStore` 已留注入点（`new ContextStore(db, { summarizer })`）——接一个 DeepSeek 低成本摘要调用（temperature 0、maxTokens 1000），在任务完成时后台执行，不阻塞主流程。
- **预期收益**：长对话 follow-up 的准确率提升；token 开销每次约 ¥0.001 级，可忽略。

### P2-8 Goal Mode（可验证目标的自检循环）
- **问题**：任务是"一次 request-response"，失败即终止，没有"自动迭代直到结论可信"的机制。
- **与 ZCode 差异**：Goal Mode 持续 plan→execute→test→review 直到目标验证完成，含状态恢复。
- **优化方向**：先做轻量版"**结论自检**"：codebase 任务产出最终答案前，自动追加一轮"逐条核对你的 findings 是否都有工具结果支撑"（一次模型调用，预算小）；后续结合 run_tests 白名单做真"红绿门"。
- **预期收益**：结论可信度提升，减少"编造结论"类失败（这正是报告里 38%→40.9% 真实成功率的主要病因之一）。

### P3-9 Plan 模式（先出方案再执行）
- **问题**：编排任务直接派发子代理，用户没有"先看拆分方案"的机会。
- **与 ZCode 差异**：Plan mode 先审后改；我们的 orchestrator 已有 suggestedSubtasks（preSplit 产出）但直接执行。
- **优化方向**：UI 加"先看拆分"开关：orchestrator 第一步只产出 subtasks 计划 → 前端展示 → 用户确认才 delegate（后端只需一个 `planOnly` 标志 + 前端确认按钮）。

### P3-10 AGENTS.md 项目约定注入 + 已读文件缓存
- **问题**：① 每次任务都从零了解工作区约定；② 同一 run 内重复 read_file 同一文件，重复消耗调用与 token。
- **与 ZCode 差异**：ZCode 读 AGENTS.md（用户级 ~/.zcode/AGENTS.md + 工作区级）作为项目约定；file-state 跟踪读过的文件。
- **优化方向**：① buildSystemPrompt 时读工作区根 AGENTS.md（若有）追加约定段——零成本对齐 ZCode/Claude Code 生态；② ToolContext 加 per-run 已读文件缓存（path→内容），同文件二次读取直接命中。

## 四、实施顺序建议

| 批次 | 内容 | 预计工作量 | 直接收益 |
|---|---|---|---|
| 第 1 批 | P0-1 重试预算 + P0-2 token 水位压缩 | 各 ~半天 | 成功率 +15pp、limit_reached 归零 |
| 第 2 批 | P1-3 并行波 + P1-4 流式工具装配 | 各 ~半天 | 运行 P95 与体感延迟大降 |
| 第 3 批 | P1-5 @ 引用 + P2-7 LLM 摘要 | 各 ~2h | 每任务省 2+ 次往返、长对话更准 |
| 第 4 批 | P2-6 错误学习 + P2-8 结论自检 | ~1 天 | 重复错误递减、结论可信 |
| 第 5 批 | P3-9 Plan 模式 + P3-10 AGENTS.md/缓存 | 各 ~2h | 可控性与成本进一步优化 |
