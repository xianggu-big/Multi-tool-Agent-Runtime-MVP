# 写能力设计原则（WRITE_PRINCIPLES）

> **一句话方针**：**写任务的能力必须始终保留**——它是 Agent 区别于聊天机器人的核心能力；任何安全问题的正确修复方向是**加强审核与回溯**，绝不是关掉、藏起或删除写能力。
> **定位**：理念层文档。实现层见 `docs/WRITE_AND_APPROVAL.md`（沙箱 + 审批的完整设计与验收）；风险面见 `reports/PROJECT_REPORT.md` 的 R14/R15/R18。
> **缘起**：2026-10-16 的真实教训——写能力曾被"默认关闭 + 界面无入口"客观隐藏，用户实测中把它误判为"根本没有写功能"，并引发跨模式误认（详见 `reports/RUN_REVIEW_2026-10-16.md`）；同日 M1' 将其修正为"能力常开、动作门控"。

---

## 1. 为什么写能力对 Agent 至关重要

1. **没有写，就没有闭环。** 「分析 → 修改 → 验证 → 修正」的自我循环依赖"改得动环境"；只能读的 Agent 永远停在建议层，每个任务都要人做最后一步。（本仓库的最小闭环样本：`code-edit` 子 Agent 的「写沙箱 → 检查阶梯 → 修正 → 提交」。）
2. **没有写，就没有真正的委托。** 委托的边界就是"对方能改变什么"。能被委托的任务，定义里必然包含"产生改变"；不能写 = 只能咨询，不能交付。
3. **没有写，可靠性反而更难建立。** 只读 Agent 把执行留给人类时，错误被藏进人机交接处（"我以为你会做"）；能写 + 能被验证的系统，才能把正确性变成**可测试的属性**（沙箱阶梯、宿主复验）。
4. **教训**：当写能力是"默认关闭 + 环境变量开启 + 界面无入口"时，对用户等效于"不存在"——Agent 被逼到"我很想帮你做，但我做不到"的难堪位置。**隐藏能力不是安全，是伪安全**：它不消除风险，只把风险转移成"用户绕过正规通道去别处冒险"。

## 2. 与聊天机器人的关键差异

| 维度 | 聊天机器人 | 写能力在线的 Agent |
|---|---|---|
| 产出物 | 文本（建议 / 草稿） | **环境状态改变**（文件 / 数据 / 服务） |
| 幻觉的代价 | 低——读一眼就能发现不对 | **高**——幻觉会直接落盘、被执行、被下游依赖 |
| 验证方式 | 人读一遍 | 必须**机器可验证**（测试 / 类型检查 / 宿主复验） |
| 信任模型 | "参考这个说法" | "相信这次改动"——需要**授权与凭证**，不是免责声明 |
| 闭环 | 说完就结束 | 写 → 验证 → 修正 → 交付 |
| 失败模式 | 说得不对 | **做错了还要有人收拾**——因此必须配好回溯 |

写能力把 Agent 从"信息产品"变成"行为主体"。**越有行为力，越需要审核与回溯**——但审核与回溯的目的是"让写能力敢用"，不是"让写能力别用"。

## 3. 总原则：capability-on, action-gated（能力常开、动作门控）

- **能力默认在线**：写工具注册可用、界面可见可选（不藏功能——用户能看见、能选择、能期待它工作）；
- **动作默认拦截**：任何具体副作用都要经过**显式授权与逐次确认**（本 run 开关 + 审批卡）；
- **失败默认安全**：通道缺失 / 校验不通过一律拒绝执行（fail-closed）；已落盘的验证失败自动回滚（fail-safe）。

**反模式（要拒绝的"假安全"）**：
- ✗ 默认关闭 + 隐藏入口（= 变相砍掉能力；M1 初版的实际形态，已由 M1' 修正）；
- ✗ 审核做成"全量阻断"（每次弹十几个确认 → 用户疲劳后无脑同意，审核名存实亡）；
- ✗ 只有纸面风险提示、没有事后证据（"文档里写了" ≠ 可回滚、可审计）；
- ✗ 出了事故就"把写能力删了"——治法是把**审核/回溯补强**（见 §6）。

## 4. 审核机制（事前 + 事中）——四道闸

| 闸 | 回答的问题 | 本仓库实现（对照） |
|---|---|---|
| ① 能力边界 | **谁能写** | `code-edit` 契约独占 `codebase:write`；主 Agent 与其余子 Agent 的工具池里没有写工具（"能力即边界"，靠结构不靠提示词） |
| ② 意图授权 | **哪一次允许写** | `orchestration.allowWriteSpecs`（界面「允许修改文件」，默认不勾）；`resolveWriteSpecsAllowed` 四处接线（契约目录 / ToolContext / delegate 守卫 / spawn 兜底），未授权 fail-closed |
| ③ 预检分离 | **先验证、后打搅** | 改动先落 Docker 沙箱暂存 → 检查阶梯（L0 语法 / L1 类型+受影响测试 / L2 全量）；**先验后批**：阶梯不通过就不弹审批 |
| ④ 人工确认 | **具体改动放行** | 审批卡（文件清单 + 逐文件 diff + 沙箱检查结果 + 三级决定：完全同意此文件 / 仅同意本次 / 拒绝）；拒绝理由回喂模型；粘性放行有边界（敏感文件永久逐次） |

设计要点：确认是**点状的**（对"这一次改动"，不是对"能力本身"）；审批要**防疲劳**（批量合并 = 一个 change set 一次审批、超时按拒绝、连续拒绝熔断）；授权与执行分层记录，为回溯提供锚点。

## 5. 回溯机制（事后）——四层

| 层 | 回答的问题 | 本仓库实现（对照） |
|---|---|---|
| ① 记录 | 发生了什么 | 全量事件流（工具调用 / 审批决定 / 子任务生命周期），SSE 可回放；单 run 报告（流程图 + 分层量化 + 六阶段归因） |
| ② 证据 | 改了什么 | diff 全量落盘（`data/sandbox/<runId>/diffs/`，事件流只带摘要）；审批决策记录（actor / 理由 / 时间） |
| ③ 恢复 | 错了怎么办 | 落盘前备份 + 原子写 + TOCTOU 哈希守卫；宿主复验失败**自动回滚**；工作区 git 化（单一写者 + 回滚安全网） |
| ④ 复盘 | 为什么会错 | 统一错误报告（三落点 + 聚合视图）；核查报告（如 `reports/RUN_REVIEW_2026-10-16.md`：逐条判定 + 证据索引）；风险登记（R14/R15/R18）驱动改进 |

设计要点：**记录必须与执行同源**（由 Runtime 生成，不依赖模型自觉——模型可能错报，事件流不会）；**证据要能脱离运行环境复核**（diff、run 报告、核查报告：不重跑也能对证）；**恢复能力与写能力同等级投入**——没有回滚的写能力才是危险的。

## 6. 边界情形：如何"既保留、又不失控"

- 对**高危动作**（删除 / 部署 / 外部副作用）：**降速，不降级**——加确认级数、缩范围（沙箱 / 白名单）、加冷却期，而不是关闭通道；
- 对**敏感资产**：逐次确认（取消粘性）、内容级过滤（敏感文件清单）、越界拒绝要带修正提示；
- 对**未知风险**：宁可 fail-closed **拒绝这一个动作**（可解释、可重试），不可 fail-closed **拒绝整个能力**；
- 对**已发生的事故**：修复顺序永远是 **回溯 → 审核 → 能力**（先补齐可恢复性，再补拦截，最后才谈能力形态）——**任何时候都不要用"删掉写能力"来结案**。

## 7. 自检清单（改动写路径时的门禁）

- [ ] 能力是否仍对用户**可见、可选、可期待**？（能力常开）
- [ ] 每个副作用是否有对应的**显式授权 + 点状确认**？（动作门控）
- [ ] 改动是否**先预检、后确认**？（先验后批）
- [ ] 全过程是否可从**事件流独立复述**？（记录）
- [ ] 每笔改动是否有 **diff 证据与审计记录**？（证据）
- [ ] 失败是否**自动回滚**、备份是否可恢复？（恢复）
- [ ] 事故是否沉淀为**核查报告与风险登记**？（复盘）
- [ ] 有没有任何一处是"为了安全而把这能力藏起来"？——**如有，改回去。**
